# Run processing through durable queue workers

AI Generation Requests and Pattern Conversions run as durable Processing Jobs rather than fire-and-forget work inside the API process. The API writes each job, its domain input, and a Job Outbox record in one PostgreSQL transaction before returning. A retrying dispatcher publishes the stable job identifier from that outbox to a Redis-backed BullMQ Processing Queue consumed by independently deployable workers. PostgreSQL remains the source of truth: Redis loss can delay delivery but cannot erase a job, and reconciliation may republish unfinished work. Queue delivery is at least once, so every worker step is idempotent, records progress durably, and may resume or retry after a crash without creating a second AI request, Pattern, credit charge, or terminal result. fal.ai callbacks reconcile against the same Processing Job instead of creating a parallel source of truth. Client and API timeouts leave the job and AI Credit Reservation pending; only provider reconciliation may declare terminal failure. Terminal success first copies the output into game-owned storage and commits the AI Artwork Library record, then captures the reservation exactly once as AI Artwork Delivery.

We accept PostgreSQL outbox dispatch, Redis and BullMQ infrastructure, worker deployment, retry policy, and reconciliation complexity in exchange for surviving API or queue restarts, scaling conversion separately from interactive requests, and making failed or delayed work observable and recoverable. CrossCraft's conversion and color-processing algorithms remain useful references, but this game owns its queue, job state, workers, data model, and backend lifecycle.
