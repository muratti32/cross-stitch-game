# Verify store purchases through RevenueCat into the commerce ledger

Apple and Google purchase verification and subscription-event normalization use RevenueCat rather than a game-built integration against the App Store Server API and Google Play Developer API. The mobile client performs purchases through the RevenueCat SDK, and the Game Backend consumes RevenueCat's server-side webhook events as its verified store input. RevenueCat is an input channel, not a source of truth: every event is applied idempotently to the game-owned Commerce Ledger, which alone decides Commerce Transaction Binding, Membership Periods, Membership Credit Grants, Stitch Coin and AI Credit grants, Commerce Reversals, and Membership Reversals under the rules of ADR-0012. The client still cannot mutate paid balances or entitlements directly, and Premium entitlement is derived from the ledger's verified state rather than read from the RevenueCat SDK on device.

Commerce Transaction Binding keys on the underlying provider transaction identifier that RevenueCat forwards, not on RevenueCat's own event or subscriber identifiers, so a future migration away from RevenueCat cannot orphan or regrant recorded transactions. Before sign-in, the RevenueCat SDK may use its own anonymous identifier only to load the Commerce Store catalog and current prices; the app never passes a Guest Installation Identity to RevenueCat and never permits that anonymous catalog session to purchase. After sign-in the SDK logs in with the Registered Account identifier, and sign-out removes that account association. The Game Backend grants only webhook events whose subscriber identity resolves to a Registered Account. Duplicate, delayed, or replayed webhook deliveries reduce to the existing idempotent grant rules, and a periodic reconciliation job compares ledger state against RevenueCat's API to detect missed events.

We accept a third-party commerce dependency, its revenue-share fee, webhook delivery and mapping work, and partial vendor lock-in on the client purchase path in exchange for provider-verified receipts without operating our own StoreKit and Play Billing verification matrix, mostly prebuilt normalization of trials, upgrades, downgrades, grace periods, billing retries, refunds, and chargebacks into the Membership Period model, and faster, safer commerce delivery for a two-platform first release.

RevenueCat TRANSFER supports moving a Membership Event or Membership Period from a Guest Installation Identity to the destination Registered Account. Transfer discovery matches either owner column, and the update sets `account_id` while clearing `guest_installation_id` in the same statement so the exactly-one-owner check remains valid. We choose this support path because the store subscription is the same verified commerce ownership, and refusing the transfer would leave the Guest entitled while the paying Account is empty.
